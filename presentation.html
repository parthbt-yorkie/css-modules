CSS Conflicts Are Real

/* global.css */ .card { background: white; } /* userCard.css */ .card { background: blue; } /* Conflicts! */

What happens:

  • Class name collisions across components
  • Unpredictable styling based on load order
  • Hard to debug - styles change unexpectedly
  • Team collaboration issues
  • Production problems with caching

The Demo Problem

Navigation Flow:

  1. Products Page → Gray theme (global CSS)
  2. Users Page → Blue theme (component CSS loads)
  3. Back to Products → Blue theme! (conflict!)
Result: Users see different styles depending on navigation path!

How CSS Modules Work

Automatic Scoping

Input: .button { background: blue; } Output: .Button_button_abc123 { background: blue; }
Component: <button className={styles.button}>Click me</button> HTML: <button class="Button_button_abc123">Click me</button>

Before vs After

Code Comparison

Before (Regular CSS): <div className="card"> <h3 className="card-title">Title</h3> </div>
After (CSS Modules): import styles from './Card.module.css'; <div className={styles.card}> <h3 className={styles.title}>Title</h3> </div>

Getting Started

1. File Naming:

ComponentName.module.css

2. Import and Use:

import styles from './Button.module.css'; <button className={styles.primary}>Click me</button>

3. TypeScript Support:

declare module "*.module.css" { const classes: { [key: string]: string }; export default classes; }

Best Practices

File Organization:

src/ components/ Button/ Button.tsx Button.module.css Button.test.tsx

CSS Structure:

/* 1. Layout */ .container { } /* 2. Typography */ .title { } /* 3. Interactive elements */ .button { } .button:hover { } /* 4. States */ .loading { }

Common Questions

Q&A

"Why not just use unique class names?"

  • Manual naming is error-prone
  • Hard to enforce across teams
  • CSS Modules automate this

"What about CSS-in-JS?"

  • CSS-in-JS has runtime overhead
  • CSS Modules have zero runtime cost
  • Better for SSR
